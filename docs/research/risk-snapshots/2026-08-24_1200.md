## TL;DR

The ~$88.44 "internal peak anchor" does not exist. It is an artifact of reading
`account_history.drawdown` — a column written in **percent** — as a **fraction**.

The prod value on 2026-08-20 was `0.02007758`, which is **0.0201 %**, not 2.01 %.
Back-solved correctly it yields a peak of **$86.67915378** — a value that is present
in session 20's `account_history` twice (rows at `2026-08-19 21:10:28` and `21:45:01`).
Nothing is unrecorded, phantom, or stale.

## 1. Which value actually populates `account_history.drawdown`

Write path (three hops, no ambiguity):

```
LiveAccountMonitor.log_account_snapshot        src/engines/live/monitoring/account_monitor.py:66
  peak_balance = performance_tracker.get_metrics().peak_balance
    → LiveEventLogger.log_account_snapshot     src/engines/live/logging/event_logger.py:180
        current_drawdown = (peak_balance - balance) / peak_balance * 100     # ← *100
      → DatabaseManager.log_account_snapshot   src/database/manager.py:1566
          AccountHistory.drawdown = current_drawdown
```

So the column is:

- **percent-valued** (`* 100`), and the column carries **no unit in its name or in
  `src/database/models.py:476`**;
- derived from **`PerformanceTracker.peak_balance`** (`src/performance/tracker.py:205,425`)
  — an in-process, non-durable peak seeded from `engine.initial_balance` and ratcheted on
  every metrics cycle;
- measured against **balance**, not equity.

That is **not** the guard's anchor, and not the circuit breaker's either. Three distinct peaks exist:

| Consumer | Peak source | Measured against | Durable across restart |
|---|---|---|---|
| `account_history.drawdown` column | `PerformanceTracker.peak_balance` (in-memory) | balance | **no** — re-anchors to recovered balance |
| `MaxDrawdownGuard` (the 20 % hard cap) | `get_session_peak_balance()` = `max(account_history.balance)` over the session lineage, then ratcheted by `observe()` | balance | **yes** |
| `AccountCircuitBreaker` | `get_session_peak_equity()` | true equity | yes (currently OFF) |
| `_durable_peak_balance()` (`trading_engine.py:2201`) | `max(guard peak, tracker peak, current balance)` | — | yes |

`drawdown_guard.py` states explicitly that the tracker peak is **never** a seed candidate.
The issue's premise — that the column reveals the guard's anchor — does not hold.

## 2. Is ~$88.44 explicable?

It never existed. Reconciliation of the actual 2026-08-20 row:

```
balance  = 86.66175070
drawdown = 0.02007758   (percent)
implied tracker peak = 86.66175070 / (1 - 0.0002007758) = 86.67915378
```

`86.67915378` is a literal `account_history.balance` value in session 20
(`2026-08-19 21:10:28.655557`, and again at `21:45:01`). Exact match, no residual.

The 0.20 % figure the standup computed independently is also correct — it used **equity**
(peak equity `86.74572304` @ 2026-08-20 00:46 vs equity `86.5748`) rather than balance.
Both numbers were right; only the unit conversion on one of them was wrong.

**Session-wide reconciliation.** Per-row implied tracker peak minus the running
`max(balance)` up to that row, aggregated by day (session 20, 1 931 rows):

| Window | max(implied peak − recorded running max) | Reading |
|---|---|---|
| 2026-06-05 → 2026-07-04 | **+15.6 to +17.2** | the known phantom-$100 book peak (pre-#851 tracker seeded from `INITIAL_BALANCE=100`) |
| 2026-07-05 → 2026-08-18 | **−1.38 to −0.01** (never positive) | post-#851; tracker peak ≤ recorded max, i.e. conservative-low after restarts |
| 2026-08-19 → today | **0.000000** | tracker peak == recorded max exactly |

The implied peak has **not exceeded a recorded `account_history` value since 2026-07-05**,
the date the #851 tracker-seeding fix reached prod. Max `drawdown` column value ever seen in
session 20 is `17.2726` (= 17.27 %, the phantom-$100 era) — again percent, not a fraction.

## Top 3 failure modes (of the reporting gap, not of the guard)

1. **Percent/fraction misread of `account_history.drawdown` recurs** and manufactures another
   phantom risk finding — or, worse, masks a real one by making 2 % look like 0.02 %.
   Early-warning signal: any computed anchor that is not a value present in
   `account_history` for the session. That check alone falsifies the reading immediately.
2. **The column is mistaken for the guard's trip metric.** It is a *different peak against a
   different quantity*. Signal: a standup assertion `guard_peak == max(account_history.equity)`
   would fail permanently, because the guard uses **balance**, not equity.
3. **Tracker-peak re-anchoring on restart** keeps the column drifting low, so it will never
   equal the guard peak after any restart. Signal: implied peak < running max in the
   reconciliation query above.

## Recommended fix (P3, housekeeping — not a live-capital change)

1. Document the unit on `AccountHistory.drawdown` (`src/database/models.py:476`) — one comment
   stating percent — and, ideally, rename to `drawdown_pct` behind a migration.
2. Persist the **guard's** peak and provenance on the snapshot row (e.g. `guard_peak_balance`,
   `peak_seed`) so the standup can assert
   `guard_peak == max(account_history.balance) over the session lineage` directly. This is the
   auditability ask in #1084 §2 and is the only part worth building.
3. The standup assertion in #1084 §3 should be written against **balance**, not equity, and
   only after (2) lands.
